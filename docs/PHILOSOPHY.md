# 判断の基準

[VISION.md](VISION.md) が「変えないもの」なら、この文書は**それをどう判断に使うか**。

---

## 1. 人が主役

主役は常に人間である。AIがユーザーに代わってすべてを決めるのではない。

ユーザーが、**何を作りたいか / 誰を助けたいか / どう動いてほしいか / 何を大切にするか**を考える。
AIはそれを理解し、整理し、設計し、実現へ近づける。

### 優先順位

1. **Human First**
2. **Community First**
3. **AI Supports Humans**
4. **Technology Serves People**

技術の新しさやAIの性能よりも、人の体験を優先する。

> ⚠️ **Community First が個人の安心・主体性を上回ってはいけない。**
> 順位は「個人が満たされた上で共同体を考える」という意味であって、
> 共同体のために個人を差し出す順序ではない。

## 2. AIは先生でも支配者でもない

AIは、何でも知っている絶対的な先生として振る舞わない。

**AIがすること:** 話を聞く / 考えを整理する / 曖昧なアイデアを言語化する /
設計図へ変換する / 選択肢を示す / 実装指示を作る / 結果を一緒に確認する / 改善を支援する

**AIがしないこと:** 答えを奪う。

人の中にある目的や思想を引き出すのが役割。

> ⚠️ **AIチームが人間を採点・指示・監視する構造にしない。**
> 行動ログを取るとしても、それは「何を見せるか」を決めるためであって、
> 「あなたは今日47回も確認しています」と指摘するためではない。

## 3. ポケットの中のコンパニオン

必要なときにすぐ呼び出せる存在を目指す。

> ポケットからスマホを出す → 相棒を呼ぶ → 今のプロジェクトを開く →
> PCを操作する → アイデアを話す → 設計書を作る → 実装を任せる → 結果を確認する

スマホは単なるリモコンではなく、**ユーザーとデジタル世界をつなぐ入口**になる。

## 役割分担

### ユーザー

- アプリで何をしたいか考える
- どんな人を助けたいか考える
- どのように動いてほしいか話す
- 大切にしたい思想を決める
- AIが作った案を評価する
- **最終判断を行う**

**高度なプログラミング知識を要求しない。**

### AI相棒（チャトピ／クロコ）

- 会話を通じて目的を把握する
- 要望を整理する
- **設計思想を守る**
- Markdown設計書を作成する
- タスクをフェーズ分けする
- 実装指示を作る
- 実装結果をレビューする
- 問題点と改善案を示す
- 過去の決定を参照する

プロジェクトマネージャー、設計補助、通訳。

### Codex

- 設計書を読む
- 指定された範囲を実装する
- テストする
- ドキュメントを更新する
- 問題点を報告する
- **勝手に思想や仕様を変更しない**

実装担当であり、**プロジェクトの目的を勝手に再定義してはならない**。

## 設計原則

### 小さく始める

最初から巨大な統合プラットフォームを作らない。**一つの明確な価値を完成させてから**拡張する。

### 部品を交換できる

AIモデル / 音声認識 / 音声合成 / 通信方式 / PC側エージェント / サーバー / 認証 /
データ保存 / UIモジュール——**特定企業や特定APIに強く依存しない**。

### ローカル優先

可能な処理はローカル端末で行う。低遅延 / プライバシー / オフライン対応 / 運用費削減 /
個人管理 / **サービス終了への耐性**。クラウドは必要な部分だけ。

### オープンであること

コアは誰でも確認でき、改造でき、フォークでき、個人サーバーで動かせる。
データを書き出せる。特定サービスに閉じ込めない。**意思決定と履歴をGitHubに残す。**

### 人とAIの両方が読めるコード

短さだけを目的にしない。責務が明確 / 名前が分かりやすい / ファイルが巨大化しない /
コメントが過剰でない / ドキュメントと実装が一致する /
**次に読むAIも、初心者の人間も、構造を追える**。

---

## データの所有権

**ユーザーのデータはユーザーのものである。**

対象: 会話履歴 / プロジェクト情報 / 設計書 / AI設定 / ショートカット / 個人設定 /
接続情報 / 作業履歴

必須:

- エクスポートできる
- 削除できる
- 保存場所を説明できる
- **勝手に学習利用しない**
- 必要以上に収集しない
- ローカル保存を選べる

保存形式は Markdown / JSON / SQLite。**人間が読める形式を優先する。**

## 誰のために作るか

### 初心者でも使える

要求しないもの: 複雑なコマンド / IPアドレスの手入力 / ポート設定 /
難しいサーバー設定 / 長いAPI設定 / エージェント構成の理解

代わりに: 自動検出 / QRコード / ワンタップ接続 / 自然言語 / 音声操作。

### 一画面一目的

機能が増えても画面を複雑にしない。操作するときは操作だけ、話すときは会話だけ、
プロジェクトを見るときはプロジェクトだけ。**高度な機能は段階的に開示する。**

### 子どもから高齢者まで

技術者専用の難しいUIにしない。分かりやすい言葉 / 大きな操作領域 / 明確なアイコン /
誤操作から戻れる / 重要操作は確認する / **色だけに意味を依存しない** / 音声でも操作できる。

> ⚠️ **開発者以外の生活を副次的に扱わない。**
> 開発の記録がよく見えるのは作者が開発者だからであって、
> 買い物や通院や家族との時間が二級の行動になってはいけない。

## 機能を足すときのチェック

1. 人が主役になっているか
2. 本当に困りごとを解決するか
3. 初心者でも理解できるか
4. スマホから自然に使えるか
5. **AIが前に出すぎていないか**
6. ローカルで動かせるか
7. データを自分で所有できるか
8. 後から部品を交換できるか
9. 小さく実装できるか
10. 全体へ自然に統合できるか

**一つでも大きく反するなら、作らない。**

そして [VISION.md](VISION.md) の門をもう一度通す——
*ユーザーが人生の積み重ねに意味を感じられるようになるか？*

---

## Codexへの開発ルール

1. この設計思想を変更しない
2. **人が主役という原則を守る**
3. 依頼されていない巨大機能を追加しない
4. MVPの範囲を守る
5. セキュリティを後回しにしない
6. ローカル優先を守る
7. 特定APIへ密結合しない
8. モジュールを交換可能にする
9. Markdownドキュメントを更新する
10. **不明点を勝手な仕様で埋めない**
11. 実装前に既存コードとドキュメントを読む
12. 変更理由を残す
13. **テストなしで完了扱いにしない**
14. 初心者が起動できるREADMEを書く
15. UIを複雑にしない
